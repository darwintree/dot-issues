# v2 规格说明

## 范围

本版本新增引用重命名系统。

当 CLI 修改 issue 文件名或路径时，系统必须自动更新同一 issue store 内其他 Markdown issue 文件中的引用，避免归档、状态变更或标题变更后留下断链。

涉及的自动触发场景：

- `modify-metadata` 导致 issue 文件名变化，例如修改 `title` 或 `status`
- `archive` 导致 issue 文件移动到 `archive/` 子树

本版本还新增手动修复命令：

- `rename-references --from <relative-path> --to <relative-path> [--dry-run]`

## 目标

本版本的目标是让 Markdown issue 文件之间的引用随文件移动保持一致：

- 自动维护标准 Markdown inline links
- 自动维护 Obsidian 兼容 wikilinks
- 避免跨出 issue store 修改仓库其他文档
- 避免通过模糊 basename 匹配造成误改
- 在批量更新失败时尽量回滚，保持 issue store 一致
- 提供独立命令用于失败后的人工排查和手动修复

## 扫描范围

引用更新只扫描当前 `--issue-dir` 下的 Markdown issue 文件。

约束：

- 包括 `archive/` 子树内的 issue 文件
- 不扫描仓库根目录下的 `README.md`
- 不扫描 `docs/` 或其他非 issue 目录
- 不扫描当前 `--issue-dir` 之外的任何文件
- 只处理 `.md` 文件

`--issue-dir` 是引用系统的边界。所有自动更新和手动重命名命令都必须以该目录为根解析路径。

## 支持的引用格式

### Markdown inline links

支持标准 Markdown inline link：

```markdown
[details](team/open_fix-login_202604011000.md)
```

支持尖括号包裹的 link destination：

```markdown
[details](<team/my issue.md>)
```

支持路径中的 URL encoding：

```markdown
[details](team/my%20issue.md)
```

支持 Markdown inline link title，并在重写时原样保留 title：

```markdown
[details](team/open_fix-login_202604011000.md "Open issue")
[details](team/open_fix-login_202604011000.md 'Open issue')
[details](team/open_fix-login_202604011000.md (Open issue))
```

重写时只替换路径部分，保留原有 query 和 fragment：

```markdown
[details](team/open_fix-login_202604011000.md?plain=1#notes)
```

### Obsidian wikilinks

支持 Obsidian 兼容 wikilinks：

```markdown
[[team/open_fix-login_202604011000]]
[[team/open_fix-login_202604011000.md]]
[[team/open_fix-login_202604011000|alias]]
[[team/open_fix-login_202604011000#Notes|notes]]
[[team/open_fix-login_202604011000#^block-id]]
```

重写时：

- 只替换文件路径部分
- 保留 alias
- 保留 heading fragment
- 保留 block fragment
- 按原链接风格保留是否带 `.md` 后缀

## 不支持的引用格式

第一版不处理 reference-style links：

```markdown
[details][issue-ref]

[issue-ref]: team/open_fix-login_202604011000.md
```

第一版不通过裸 basename 做模糊匹配。

例如以下 Obsidian 链接不会被自动更新：

```markdown
[[open_fix-login_202604011000]]
```

原因是同一个 issue store 内可以通过 `--subdir` 创建同名 basename：

```text
.issues/team-a/open_fix-login_202604011000.md
.issues/team-b/open_fix-login_202604011000.md
```

所有可更新引用都必须包含可从引用所在文件解析到旧 issue 文件的相对路径。

## Markdown 链接排除规则

系统只处理本地相对 `.md` issue 路径。

以下链接目标必须跳过：

```markdown
[web](https://example.com/a.md)
[email](mailto:a@b.com)
[anchor](#section)
[root](/absolute/path.md)
[file](file:///tmp/a.md)
[image](./diagram.png)
```

排除规则：

- 跳过带 scheme 的 URL
- 跳过 mailto 等非文件链接
- 跳过页内 anchor
- 跳过绝对路径
- 跳过非 Markdown 文件
- 跳过解析后不指向旧 issue 文件的路径

## 路径解析规则

所有链接目标都按引用所在文件的位置解析。

示例：

```text
.issues/team/a.md
.issues/team/b.md
```

如果 `team/a.md` 中引用：

```markdown
[b](b.md)
```

则该链接解析为：

```text
.issues/team/b.md
```

重写后的路径也必须相对于引用所在文件生成。

示例：`team/b.md` 被归档到 `archive/team/closed_b_202604011000.md` 后，`team/a.md` 中引用应变为：

```markdown
[b](../archive/team/closed_b_202604011000.md)
```

而不是：

```markdown
[b](archive/team/closed_b_202604011000.md)
```

## 被移动文件的出站链接重算

当某个 issue 文件被移动到新路径时，该文件正文中指向其他 issue 文件的相对链接也必须按移动后的文件位置重新计算。

这类链接的目标文件本身没有移动，但链接所在文件的位置变了；如果不重算，相对路径会在移动后失效。

示例：

```text
.issues/team/backend/working_a_202604011000.md
.issues/team/frontend/open_b_202604011100.md
```

如果 `team/backend/working_a_202604011000.md` 正文中引用：

```markdown
[b](../frontend/open_b_202604011100.md)
[[../frontend/open_b_202604011100|B]]
```

归档后，文件移动到：

```text
.issues/archive/team/backend/closed_a_202604011000.md
```

该文件正文中的引用应重算为：

```markdown
[b](../../../team/frontend/open_b_202604011100.md)
[[../../../team/frontend/open_b_202604011100|B]]
```

约束：

- 只对被移动文件自身正文中的出站链接执行这种重算
- 只重算能解析到当前 `--issue-dir` 内已知 issue 文件的链接
- 不对其他文件中的无关出站链接做全局重算
- 保留 Markdown query 和 fragment
- 保留 Obsidian alias、heading fragment、block fragment
- 按原链接风格保留是否带 `.md` 后缀

## 后缀保留规则

重写后是否带 `.md` 后缀取决于原链接风格。

规则：

- 原来带 `.md`，重写后继续带 `.md`
- 原来不带 `.md`，重写后继续不带 `.md`
- Markdown inline links 通常会带 `.md`
- Obsidian wikilinks 可以带或不带 `.md`

示例：

```markdown
[[team/open_fix-login_202604011000|Fix]]
```

归档后变为：

```markdown
[[../archive/team/closed_fix-login_202604011000|Fix]]
```

## 自引用规则

被移动 issue 文件正文中指向自身的引用也必须更新。

示例：

```markdown
[this issue](open_a_202604011000.md)
[[open_a_202604011000|self]]
```

归档后，如果文件移动到：

```text
archive/closed_a_202604011000.md
```

自身正文中的引用应按移动后的文件位置重算，变成：

```markdown
[this issue](closed_a_202604011000.md)
[[closed_a_202604011000|self]]
```

## Front matter 处理规则

引用重写只处理 Markdown 正文，不处理 front matter。

约束：

- 不扫描 front matter 中的字符串
- 不因为引用重写重新序列化 front matter
- 不新增 front matter 字段
- 不修改 front matter 中的非目标字段

如果未来需要在 metadata 中表达 issue 关联，应设计明确结构化字段，而不是通过字符串链接扫描实现。

## 时间戳策略

自动引用重写不触碰被动更新文件的 `updated_at`。

规则：

- `modify-metadata` 仍更新目标 issue 的 `updated_at`
- `archive` 仍更新目标 issue 的 `updated_at`
- 自动被修复引用的其他 issue 文件不更新 front matter
- `rename-references` 不更新任何 issue 的 front matter

`updated_at` 表示 issue metadata 或正文的人工变更时间，不应因为存储完整性维护产生噪音。

## 一致性与回滚

`modify-metadata` 和 `archive` 在文件路径变化时，引用更新是同一操作的一部分。

如果引用更新失败，命令应整体失败，并尽量回滚已经完成的文件操作。

推荐执行流程：

1. 验证目标 issue 路径不存在。
2. 扫描 `--issue-dir` 下所有 Markdown issue 文件。
3. 计算引用更新计划。
4. 移动目标 issue 文件。
5. 写入目标 issue 的新 front matter 和原正文。
6. 写入所有需要更新引用的 issue 正文。
7. 如果任一步失败，尽量恢复旧 issue 文件、旧 front matter、旧正文，以及已经写过的引用文件内容。

这是本地文件系统上的尽力回滚，不提供数据库事务级保证。

## `modify-metadata` 返回数据变更

`modify-metadata` 的 JSON 返回值需要在保持兼容的基础上增加引用更新统计。

当前兼容字段继续保留：

```ts
data: { issue, path }
```

新增字段：

```ts
data: {
  issue,
  path,
  references: {
    filesChanged,
    referencesChanged
  }
}
```

如果没有引用被更新，统计值为 `0`。

## `archive` 返回数据变更

`archive` 的 JSON 返回值需要在保持兼容的基础上增加引用更新统计。

当前兼容字段继续保留：

```ts
data: { issue, path }
```

新增字段：

```ts
data: {
  issue,
  path,
  references: {
    filesChanged,
    referencesChanged
  }
}
```

如果没有引用被更新，统计值为 `0`。

## 新增命令：`rename-references`

新增命令用于手动重写引用，不移动文件，不修改 front matter。

命令格式：

```bash
bun {skillPath}/scripts/index.ts rename-references --from <relative-path> --to <relative-path> [--issue-dir .issues] [--dry-run]
```

行为：

- `--from` 是旧 issue 路径
- `--to` 是新 issue 路径
- 两者都相对 `--issue-dir`
- 只扫描当前 `--issue-dir` 下所有 `.md` issue 文件
- 包括 `archive/` 子树
- 只更新 Markdown 正文
- 不移动文件
- 不修改 front matter
- 不要求 `--from` 当前仍然存在
- 不要求 `--to` 当前已经存在

允许 `--from` 或 `--to` 指向当前不存在的文件，是为了支持自动重命名失败后的手动排查和修复。

## `rename-references` 路径校验

`--from` 和 `--to` 必须满足以下规则：

- 必填
- 必须是非空字符串
- 必须是相对路径
- 拒绝绝对路径
- 规范化 `.` 和 `..`
- 规范化后不得逃出 `--issue-dir`
- 接受带或不带 `.md` 后缀
- 内部统一规范化为带 `.md` 的 issue-relative path
- 拒绝非 `.md` 目标
- JSON 输出和错误信息使用规范化后的 `/` 分隔相对路径

示例：

```bash
rename-references --from team/open_a_202604011000 --to archive/team/closed_a_202604011000
```

内部等价于：

```text
from: team/open_a_202604011000.md
to: archive/team/closed_a_202604011000.md
```

## `rename-references --dry-run`

`--dry-run` 只计算变更计划，不写入文件。

成功输出示例：

```json
{
  "success": true,
  "message": "References analyzed successfully",
  "data": {
    "from": "team/open_a_202604011000.md",
    "to": "archive/team/closed_a_202604011000.md",
    "filesChanged": 2,
    "referencesChanged": 3,
    "changes": [
      {
        "path": "/abs/.issues/a.md",
        "referencesChanged": 1
      }
    ]
  }
}
```

非 dry-run 成功输出示例：

```json
{
  "success": true,
  "message": "References renamed successfully",
  "data": {
    "from": "team/open_a_202604011000.md",
    "to": "archive/team/closed_a_202604011000.md",
    "filesChanged": 2,
    "referencesChanged": 3,
    "changes": [
      {
        "path": "/abs/.issues/a.md",
        "referencesChanged": 1
      }
    ]
  }
}
```

## 错误语义

相关命令采用显式失败，不做静默降级。

- `modify-metadata` 目标路径已存在时失败
- `archive` 目标路径已存在时失败
- `modify-metadata` 或 `archive` 引用更新失败时整体失败并尽量回滚
- `rename-references` 路径参数非法时失败
- `rename-references --dry-run` 不写入任何文件
- 无引用需要更新时，命令成功，统计值为 `0`

本版本至少需要覆盖以下场景：

- `modify-metadata` 改 `status` 后更新 Markdown inline links
- `modify-metadata` 改 `title` 后更新 Obsidian wikilinks
- `archive` 后更新嵌套目录中的相对 Markdown links
- `archive` 后更新被移动文件自身正文里的自引用
- `archive` 或 `modify-metadata` 移动文件后，重算被移动文件正文中指向其他 issue 的相对链接
- 保留 Markdown link 的 query 和 fragment
- 保留 Markdown inline link title
- 保留 Obsidian alias、heading fragment、block fragment
- 按原风格保留是否带 `.md` 后缀
- 跳过外部 URL、anchor、绝对路径、非 Markdown 链接
- 只更新正文，不修改 front matter
- 自动引用更新不触碰其他 issue 的 `updated_at`
- `rename-references --dry-run` 输出计划但不写文件
- `rename-references` 在 `--from` 不存在时仍可执行
- `rename-references` 拒绝逃出 `--issue-dir` 的路径
- 目标路径冲突或写入失败时不留下部分更新
